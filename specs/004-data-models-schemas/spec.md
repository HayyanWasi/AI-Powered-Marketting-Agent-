# Feature Specification: Data Models & Schemas

**Feature Branch**: `004-data-models-schemas`
**Created**: 2026-07-14
**Status**: Draft
**Input**: User description: "Define all data structures as Python dataclasses and Pydantic schemas with validation. FR-05, FR-10."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Developer Defines Guest Profile Structure (Priority: P1)

As a developer building the event guest workflow, I want a validated Guest profile model with name, title, company, and bio fields, so that speaker/guest data is consistently structured and validated before being stored or displayed.

**Why this priority**: Guest profiles are a core data entity used by campaign generation agents and the frontend. Without a well-defined model, guest data would be inconsistent, causing integration bugs downstream.

**Independent Test**: A Guest profile can be created with all fields populated, serialized to a portable format (e.g., JSON), deserialized back, and all field values are preserved correctly. Required fields reject empty values.

**Acceptance Scenarios**:

1. **Given** a new guest profile with name, title, company, and bio, **When** validated, **Then** the data passes validation and is ready for use.
2. **Given** a guest profile with a missing name, **When** validated, **Then** the system rejects with a "name is required" error.
3. **Given** a valid guest profile, **When** serialized to JSON and deserialized back, **Then** all field values match the original.

---

### User Story 2 - Developer Defines Campaign Data Structure (Priority: P1)

As a developer building the campaign generation pipeline, I want a validated Campaign model with type, caption, image URL, and status fields, so that generated campaigns have a consistent structure that the frontend and storage layer can rely on.

**Why this priority**: Campaigns are the primary output of the system. Every campaign generated by agents must follow the same structure for display, storage, and validation.

**Independent Test**: A Campaign can be created with a valid type and caption, serialized and deserialized without data loss, and invalid type values are rejected at validation time.

**Acceptance Scenarios**:

1. **Given** a campaign with a recognized type and caption, **When** validated, **Then** the campaign passes validation.
2. **Given** a campaign with an empty caption, **When** validated, **Then** the system rejects with an appropriate error.
3. **Given** a valid campaign, **When** its status transitions through valid states, **Then** each transition is accepted; invalid transitions are rejected.

---

### User Story 3 - Developer Defines Company Profile Structure (Priority: P1)

As a developer integrating brand profile management, I want a validated Company model with id, name, brand tone, and reference image URLs, so that the company's brand identity is consistently represented across all campaign outputs.

**Why this priority**: Company profiles are referenced by every campaign and agent. Consistent structure ensures brand rules are applied uniformly.

**Independent Test**: A Company profile can be created with name and tone, serialized to JSON and back, and the reference image URLs list is correctly handled when empty or populated.

**Acceptance Scenarios**:

1. **Given** a company profile with name and brand tone, **When** validated, **Then** the data passes validation.
2. **Given** a company profile with an empty name, **When** validated, **Then** the system rejects with "name is required".
3. **Given** a company profile with up to 6 reference image URLs, **When** serialized, **Then** the URL list is preserved exactly.

---

### Edge Cases

- **Empty strings for required fields**: Required text fields (name, caption) reject empty or whitespace-only values.
- **Missing optional fields**: Optional fields (bio, image_url, reference_image_urls) can be omitted without error.
- **Extremely long text values**: Very long name, bio, or caption values should be accepted up to a practical limit; excessively long values should be rejected.
- **Campaign status transitions**: Only valid status transitions should be permitted (e.g., from draft to published, not from published back to draft unless explicitly allowed).
- **Invalid campaign type**: An unrecognized campaign type string should be rejected with a clear error listing valid types.
- **Image URL format**: Image URLs should be valid URLs; malformed URLs should be flagged.
- **Reference image URL list limits**: Company profiles enforce a maximum of 6 reference image URLs.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-05-01**: System MUST define a Guest data model with fields: name (required), title (optional), company (optional), bio (optional).
- **FR-05-02**: Guest name MUST be a non-empty string; blank or whitespace-only values MUST be rejected.
- **FR-05-03**: System MUST define a Campaign data model with fields: type (required), caption (required), image_url (optional), status (required).
- **FR-05-04**: Campaign caption MUST be a non-empty string; blank or whitespace-only values MUST be rejected.
- **FR-05-05**: Campaign status MUST be one of a defined set of lifecycle states (e.g., draft, published, archived).
- **FR-05-06**: System MUST define a Company data model with fields: id (required, auto-generated), name (required), tone (required), reference_image_urls (optional, list).
- **FR-05-07**: Company name MUST be a non-empty string; blank or whitespace-only values MUST be rejected.
- **FR-05-08**: All three data models MUST support serialization to a portable text format (e.g., JSON) with zero data loss.
- **FR-05-09**: All three data models MUST support deserialization from a portable text format back to the original model.
- **FR-05-10**: Optional fields MUST be omitted (or set to a safe default) when not provided — never raise errors for missing optional fields.
- **FR-05-11**: Image URL fields MUST accept valid URL strings; invalid URLs SHOULD be flagged.
- **FR-10-01**: All data models MUST enforce type validation on every field (e.g., strings must be strings, lists must be lists).
- **FR-10-02**: Validation errors MUST produce clear, human-readable messages identifying the specific field and the reason for rejection.

### Key Entities

- **Guest Profile**: An event speaker or attendee with biographical information (name, title, company, bio) used in campaign content generation.
- **Campaign**: A generated social media campaign output containing type classification, the caption text, an optional generated image URL, and a workflow status.
- **Company Profile**: A marketing organization's brand identity record with a unique identifier, name, brand tone, and optional collection of reference image URLs.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All three data models can be instantiated with valid data, serialized to JSON, deserialized, and produce identical field values with zero data loss.
- **SC-002**: Invalid data (empty required fields, wrong types, unknown status values) is rejected 100% of the time with a clear, field-specific error message.
- **SC-003**: Optional fields can be omitted from input without causing validation or runtime errors.
- **SC-004**: All models pass static type checking without errors.
- **SC-005**: 100% of defined data model code paths have corresponding tests covering both valid and invalid data scenarios.
